接案當 PM 之後，我每天最常在想的不是「這個功能怎麼做」，而是下面這三個問題：

* **執行者現在做到哪了？**
* **他這幾天到底有沒有在做？**
* **有哪些事情卡住了，需要我去跟客戶釐清？**

然後客戶那邊，一定會再丟過來第四個問題：「請問現在到哪了？」😂

這幾個問題聽起來很簡單，但每一個都很難回答。最好笑的是，有時候東西**其實早就做好了，只是我不知道**😂 執行者做完了沒說，我也沒問，進度就這樣卡在我的腦袋裡。

要回答客戶「到哪了」，我得先把前面三個問題都問完一輪，再自己拼成一份像樣的報告。

所以這個月，我做了一個專案管理系統：**一個把 PM、客戶、執行者三方連在一起的中控台**。

> **一句話：執行者只回報「哪些做完了」，客戶不用註冊就看得到進度、做得了決定，PM 直接跟 AI 對話維護整個專案；進度和燈號由系統用資料算，不靠感覺填。**

今天就來分享一下：

* 接案 PM 的三個痛，以及為什麼一般的專案管理工具沒有解決它
* 這個系統怎麼讓三方各看各的、各做各的
* 我最喜歡的部分：**PM 直接跟 AI 對話，就能維護整個專案、查進度、寫週報**
* 進度為什麼要「用算的」，以及它幫我抓到的一顆西瓜🍉
* 真實的使用數字，跟它是怎麼做出來的

## 接案 PM 的三個痛

### 痛一：不知道做到哪

不知道做到哪，有兩種。

第一種是**做好了，但我不知道**。執行者做完就去忙下一件了，沒有特別回報；我以為還在做，客戶問起來，我只能說「我再確認一下」。明明是好消息，卻因為沒人講，變成一個要去追的問題。

第二種是**還沒好，但看起來快好了**。專案管理裡有一個很有名的現象，叫 **「90% 症候群」**：一個任務很快就做到 90%，然後剩下的 10% 又花了跟前面一樣久。

問題出在「90%」這個數字是**估出來的**。執行者真心覺得自己快做完了，但「快做完」跟「做完」中間，常常還藏著測試、修 bug、等客戶給素材……

這兩種的解法其實是同一個：與其問「做到幾 % 了」，不如讓大家回報「**哪些做完了？**」，而且回報要輕到做完順手就會按。做完就是做完，沒做完就是沒做完，沒有中間值。

### 痛二：不知道有沒有在做

接案的團隊通常很分散：有外包的工程師、有兼職的設計師，大家不在同一個辦公室，你看不到他今天在忙什麼。

在這之前，我是用一個資料夾管專案的：每個工項一個 Markdown 檔，再寫幾個 AI skill 幫我整理進度、產生給客戶看的進度頁。從 8 月開始，一個專案就累積了 34 個工項。

它其實挺好用的，但有一個根本的問題：**所有進度都要經過我。** 執行者跟我說「首頁做完了」，我再叫 AI 寫進去。他沒說，我就不知道；我忙到忘了寫，進度頁就停在上禮拜。

資料只有我一個人在維護，那它永遠只會跟我的記憶力一樣好😫

### 痛三：不知道有什麼要釐清

接案最常卡住的，往往不是技術，而是**等客戶**：等素材、等帳號、等他決定要 A 方案還是 B 方案。

這些事情散在 LINE、Email、會議裡。客戶在會議上口頭答應了某件事，兩個月後再問「不是說 3 月底嗎？」，誰也想不起來當初是怎麼講的。

還有一種更麻煩的：範圍悄悄變大。客戶在 LINE 上說「這邊順便加一個小功能」，每一個都很小，加起來就是兩個禮拜。

### 為什麼一般的專案管理工具沒解決

市面上的專案管理工具很多：Trello、Asana、Jira、Notion……

它們都很強，但它們是**做給「團隊內部」用的**。接案有一個很不一樣的地方：**你有一個外部的客戶**，而客戶：

* 不會想為了看進度，去註冊一個帳號、學一套新工具
* 不應該看到所有內部任務、內部討論（團隊內部的討論，你不一定想讓客戶看到😂）
* 真正需要的只有兩件事：**現在到哪了，以及有什麼要我決定的**

而且這些工具的資料結構都要自己設計：欄位怎麼開、狀態有哪些、進度怎麼算。專案管理的 know-how，全部要自己帶進去。

## 一個連結三方的中控台

所以我做的這個系統，核心的想法是：**三個角色，各看各的、各做各的，但大家看的是同一份資料。**

| 角色 | 是誰 | 打開它是為了 |
|---|---|---|
| **PM** | 我，接案、跟客戶溝通、拆任務排時程的人 | 維護計畫、看風險、寫週報 |
| **執行者** | 工程師、設計師，真正做事的人 | 看「我要做什麼」，回報「哪些做完了」 |
| **Stakeholder** | 客戶窗口、出錢驗收的人 | 看「到哪了」、決定「要我決定的事」 |

下面一個一個來看～

## 執行者：只回報「哪些做完了」

給執行者的設計，我只追求一件事：**回報要夠輕，輕到他願意做。**

* 打開「我的工作」，勾選做完的任務，按回報，結束
* 不用估百分比
* 只做完一部分？**把任務拆成子任務，勾掉做完的那幾個**。例如「串接金流」拆成「建立訂單 API」「付款回傳」「退款」，做完一個勾一個
* 卡住了就標「卡關」，寫原因跟需要誰

![執行者的「我的工作」：只列自己負責的任務，依期限分好，做完就勾（示範資料）](https://storage.googleapis.com/homuchen.com/images/ai-project-management-system-executor.jpg)

這樣一來，「90%」這個數字就消失了。上層任務的完成度，由子任務自動算出來，不能手填。

執行者也可以用自己的 AI 回報：跟它說「今天登入頁做完了，API 串接做一半」，AI 會找到對應的任務，提議把「API 串接」拆成子任務，確認後一次回報上去。

## 客戶：不用註冊，一頁看懂

客戶這邊，我花最多心思的是「**他不用做任何事，也能知道狀況**」。

* **不用註冊**：PM 輸入客戶的名字和 Email 就加進來了
* **個人連結**：每位客戶有自己的進度頁連結，點開就能看，不用登入
* **週報直接寄到信箱**：PM 發週報，系統寄給每一位客戶，信裡帶著他自己的進度頁連結
* **只看給客戶看的**：內部任務、內部議題、留言都看不到；他只看得到整體進度、里程碑、週報，還有指派給他的事

![客戶的進度頁：不用登入，看得到整體進度、要他決定的事、要他提供的東西（示範資料）](https://storage.googleapis.com/homuchen.com/images/ai-project-management-system-client.jpg)

### 「要你決定的事」變成一張張卡片

前面說的「等客戶決定」，在這裡會被開成一個**待決定事項**：要決定什麼、有哪幾個選項、PM 建議哪一個、什麼時候前要。

客戶會收到一封「要你決定」的信，在進度頁上直接選就好。過了期限還沒決定，系統會在燈號上提醒我。

### 客戶在 LINE 上說的，也算數

老實說，大部分客戶還是不會自己登入的😂 他們習慣開會講、LINE 講。

所以系統讓 PM 可以**代為記錄**：客戶在 LINE 上說「好，就用 A 方案」，我記下來的時候會寫「是哪位客戶決定的、經由什麼管道」。介面上會顯示像「張董 · LINE · 陳柏宇記錄」這樣的字，誰決定的、誰記錄的分開記。

兩個月後再有人問「當初誰說的？」，翻得出來。

### 「不是說 3 月底嗎？」答得出來

專案從「規劃中」改成「進行中」的時候，系統會自動拍一張**基準線**：當下承諾的目標日、每個里程碑的日期、範圍裡有哪些任務。客戶確認，就等於同意了這份計畫。

之後日期怎麼移、任務怎麼加，系統都會跟基準線比，列出「還沒經過核准的變更」。客戶在 LINE 上「順便加的小功能」，在這裡會現形。

## PM：直接跟 AI 對話管專案

好啦，這是我最想分享的部分😎

身為 PM，我大部分的時間其實不是花在「做決定」，而是花在**維護資料**：把會議記錄裡的待辦變成任務、更新期限、把三個專案的狀況整理成週報。

這個系統從第一天就是設計給 AI 用的。它有一個 [**MCP**](https://modelcontextprotocol.io/)（Model Context Protocol）介面，接上 Claude 或 ChatGPT 之後，我就可以直接用講的：

> 「讀這個資料夾的需求文件，幫我拆成里程碑和任務，排到 3 月底前，建進去。」

AI 會先讀需求，把不清楚的地方問我，再用表格給我看它打算怎麼拆：每個里程碑有驗收標準、每個任務有估計工時跟前置關係。我確認之後，它一次建好，最後再跑一次計畫檢查。

> 「這幾個專案現在怎樣？」

它會列出每個專案的燈號、實際進度跟計畫進度、逾期跟卡關的任務。

> 「這週的週報寫一下。」

它讀這週的進度和動態，草擬一份四段式的週報：本期完成、下期計畫、風險與議題、需要你決定的事。給我看過、我改完，它才發出去寄給客戶。

> 「客戶剛剛在 LINE 說首頁的 banner 要換成影片。」

可以請它幫我判斷這算不算範圍變更，要不要開一個變更請求、要不要跟客戶確認影響幾天。

如果你看過我之前寫的 [**MCP / Tools / Skills：AI Agent 的三種能力擴充**](/posts/mcp-tools-skills/)，這就是一個 MCP 的實際例子：**系統把專案管理的能力包成工具，AI 負責聽懂我在說什麼、決定要用哪個工具。**

接法也很簡單。在 claude.ai 或 ChatGPT 的自訂連接器貼上網址 `https://pm.homuchen.com/mcp`，登入、按允許就好。用 Claude Code 的話，一行指令：

```sh
claude mcp add --scope user --transport http pm https://pm.homuchen.com/mcp --header "Authorization: Bearer <你的存取金鑰>"
```

### AI 改了什麼，都查得到

讓 AI 改專案資料，大家一定會擔心：「它亂改怎麼辦？」

所以每一筆修改都會記下來：**誰改的、經由網頁還是 AI、改了哪個欄位、前後的值**。總覽頁還會列出 AI 最近三天改了什麼。系統內建的手冊也規定：發週報、刪除、改期限這種會影響別人的事，AI 要先給我看內容，我說 OK 才送出。

還有一件我很在意的事：**AI 的權限跟我一樣，不會比我多。** 介面、API、MCP 走的是同一套規則，我在網頁上不能做的事，AI 也做不到。

## 進度是算出來的，不是填的

前面一直提到「燈號」，這邊要特別講一下，因為這是我覺得最重要的設計。

專案管理有一個詞叫 [**西瓜報告**](https://www.cascade.app/blog/watermelon-reporting)🍉（watermelon reporting）：外面綠、裡面紅。週報上每週都寫「正常」，直到最後一週突然變紅，大家都傻眼。

會這樣通常不是 PM 故意說謊，而是燈號是**用感覺填的**。沒有人想當第一個報壞消息的人。

所以在這個系統裡：

* **實際進度**：只算最底層的任務，依估計工時加權
* **計畫進度**：照每個任務的開始日到期限，算出「到今天應該完成多少」
* **SPI** = 實際進度 ÷ 計畫進度。0.95 以上算正常，0.8 到 0.95 有風險，0.8 以下落後
* **系統建議燈號**：綜合 SPI、逾期的里程碑和任務、卡關、高分風險、過期沒決定的事

PM 還是可以自己決定燈號，但**如果比系統樂觀，一定要寫原因**，而且客戶會同時看到「PM 評估」跟「系統指標」兩個燈號。

![儀表板：先放要處理的事，下面是燃起圖、基準線偏差與燈號歷史（示範資料）](https://storage.googleapis.com/homuchen.com/images/ai-project-management-system-dashboard.jpg)

### 搬進來第一天，就抓到一顆西瓜

做好之後，我把手上進行中的 4 個客戶專案搬進來，總共 205 個任務。之前做完的工作，可以補登當初完成的日子，所以燃起圖跟預估完成日都是照真實的時間算的。

其中一個專案，搬進來的時候燈號是「正常」。系統一算：

| 指標 | 數字 |
|---|---|
| 實際進度 | 67% |
| 照計畫應該完成 | 77.6% |
| SPI | 0.86 |
| 逾期的里程碑 | 1 個 |
| 逾期的任務 | 3 個 |
| 卡關的任務 | 2 個 |
| 處理中的議題 | 8 個 |

**系統建議：落後。** 預估完成日也比目標日晚了三個多禮拜。

說實話，這些事情我心裡大概都知道，但「大概知道」跟「看到這張表」是兩回事😱 它逼我去面對：這個專案靠團隊自己已經拉不回來了，要跟客戶談範圍或時程。

## 順便說一下：它是怎麼做出來的

這個系統一樣是我跟 Claude Code 一起做的。11/16 下午兩點開工，到 11/17 晚上，兩天 87 個 commit，大約 27,000 行 TypeScript、16 個測試檔。

會這麼快，一個很大的原因是**我不是從零開始**。上個月我做了 [**自己的 AI 助理**](/posts/claude-code-ai-assistant-one-day/)，把 LINE、Gmail、會議錄音全部收進來，那時候已經把登入、權限、部署、MCP 這些基礎都做好了。這次直接把骨架搬過來，專心做專案管理本身。

但老實說，這次花最多時間的不是寫程式，而是**想清楚專案管理該怎麼做**：進度怎麼算、燈號怎麼判斷、客戶該看到什麼、不該看到什麼。我還叫 AI 對照網路上的專案管理實務，幫我做了一次 review，基準線、防西瓜報告、待決定事項，都是那次 review 之後補上的。

程式交給 AI，**想清楚要什麼，還是自己的事**。這跟我在 [**五月才過七天，我快有 500 個 commits**](/posts/ai-labor-not-tool-500-commits/) 裡寫的一樣：AI 在替我幹活，但要它做什麼，得我說清楚。

## 常見問題

### 接案 PM 怎麼追執行者的進度，又不用一直問？

讓回報變得很輕：只回報「哪些做完了」，做一半就拆子任務，卡住就標卡關。PM 看的進度、燈號、預估完成日都從這些回報自動算出來，不用一個一個去問。

### 什麼是西瓜報告？

專案狀態報告「外面綠、裡面紅」：週報上一直寫正常，實際上早就落後，等到最後才突然變紅。解法是讓燈號有數據根據，例如 SPI、逾期的里程碑、卡關的任務，PM 的判斷比數據樂觀時要寫原因。

### SPI 是什麼？怎麼算？

SPI（Schedule Performance Index，進度績效指標）= 實際完成的進度 ÷ 照計畫到今天應該完成的進度。1 代表剛好照計畫，小於 1 代表落後。這個系統用 0.95 以上算正常、0.8 到 0.95 有風險、0.8 以下落後。

### 跟 Notion、Trello、Jira 差在哪？

它們是通用的工具，資料結構和流程要自己設計。這個系統是**特化給接案的專案管理**：角色、進度算法、週報格式、燈號判斷都是內建的，而且多了一個「外部客戶」的角色。代價是比較沒彈性，例如不能自訂欄位和流程。

### 客戶要註冊嗎？

不用。PM 輸入名字和 Email 就加進來了，客戶用個人連結看進度、做決定、驗收，也會收到週報的信。

### 支援哪些 AI？

有 MCP 的都可以：Claude Code、Claude 桌面版、claude.ai 的連接器、ChatGPT 的連接器。也有 REST API，可以自己寫腳本接。

### 執行者也要會用 AI 嗎？

不用。執行者在網頁上勾選做完的任務就好。會用 AI 的話，也可以用講的回報。

### 有工時、請款的功能嗎？

目前沒有。第一版刻意不做金流、工時打卡和請款，先把「大家看同一份進度」這件事做好。
